# PS 端软件架构设计文档

## 1. 文档目的

配套执行规则见 [CONFORMANCE_RULES.md](./CONFORMANCE_RULES.md)，用于将本文的架构原则落地为可检查的命名、分层、接口与验证约束。

本文档用于约束 `src/ps/app/src` 下 PS 端软件的目录组织、分层关系、模块职责、依赖方向、上下文建模方式以及后续扩展规范，目标是让该工程在持续演进过程中始终保持：

- 高内聚、低耦合
- 单一职责、边界清晰
- 目录结构稳定、可扩展
- 编译期依赖可控、变更影响面可预测
- 可复用模块与项目专属模块明确分离

本文档既是当前代码结构说明，也是后续新增模块、拆分文件、重构边界时的执行标准。

## 2. 适用范围

适用目录：`Zynq-GBA_MisTer-Vivado/src/ps/app/src`

适用对象：

- PS 端应用入口
- PS 端应用编排逻辑
- 项目专属视频、诊断、GBA 寄存器控制逻辑
- 可复用基础模块，如 Audio、Vdma、Storage
- 与上述模块相关的公共状态定义和上下文装配逻辑

不直接约束但需要配合的对象：

- Vitis/FreeRTOS 工程配置
- 平台导出目录
- 第三方中间件和 BSP

## 3. 架构目标

### 3.1 主目标

1. `main.c` 只负责系统启动和装配，不承载业务细节。
2. 可复用能力必须从项目逻辑中抽离，形成独立模块。
3. 项目逻辑按领域拆分，避免“大文件 + 全局对象 + 横向穿透调用”。
4. 通过窄上下文和服务句柄限制模块可见面，降低编译期耦合。
5. 通过 `Inc/Src` 分离公开接口与实现细节，控制依赖扩散。

### 3.2 非目标

以下事项不是本文档追求的目标：

- 为了“看起来层次多”而机械增加目录层级
- 为了抽象而抽象，制造无意义中间层
- 过度模板化，牺牲嵌入式场景下的可读性和可调试性
- 把所有状态做成动态分配对象

## 4. 核心设计原则

### 4.1 单一职责原则

每个模块只处理一种稳定变化原因：

- `Video` 负责采样、缩放、显示帧呈现
- `Rom` 负责 ROM 装载规则
- `Storage` 负责 FatFs 文件访问
- `Audio` 负责音频编解码器驱动
- `Gba` 负责项目专属寄存器访问

### 4.2 关注点分离

必须显式区分以下几类代码：

- 启动装配代码
- 运行时编排代码
- 领域逻辑代码
- 设备/驱动访问代码
- 调试/审计代码
- 纯状态定义

### 4.3 依赖方向单向

依赖必须从高层向低层流动，禁止反向依赖和环依赖。高层可以调用低层，低层不能感知高层。

### 4.4 窄接口优先

模块之间不应传递“全局总对象”，而应传递该模块实际需要的最小上下文。
例如：

- `Video` 不需要知道 UART 和 Audio，就不应看到它们
- `Diagnostics` 需要观察多个模块，但不应拥有应用编排职责
- `Rom` 不需要知道 FatFs 细节之外的业务逻辑

### 4.5 组合根唯一

完整应用对象只能在组合根中出现。
当前组合根包括：

- `main.c`
- `Common/Inc/ps_app_context.h`
- `Common/Src/ps_app_context.c`

除组合根外，其他功能模块不得依赖完整 `PsAppContext`。

### 4.6 状态与行为分离

纯状态定义应尽量与行为实现拆开：

- 状态定义放在 `Common/Inc/ps_app_state.h`
- 行为接口放在各自模块的 `Inc`
- 对象装配放在 `Common/Src/ps_app_context.c`

这样可以减少头文件传播和不必要的重新编译。

### 4.7 可复用能力优先下沉

凡是与具体项目业务无关、在其他项目也可能复用的模块，必须优先下沉为独立基础模块，例如：

- `Audio`
- `Vdma`
- `Storage`

凡是带有本项目语义、寄存器约束、链路约束、协议约束的模块，保持在项目专属域，例如：

- `Gba`
- `Video`
- `Diagnostics`
- `Rom`

## 5. 总体分层模型

### 5.1 分层说明

当前 PS 端推荐采用以下五层模型：

1. 入口装配层
2. 应用编排层
3. 领域功能层
4. 可复用基础设施层
5. 硬件访问与平台适配层

### 5.2 分层职责

| 层级 | 说明 | 当前目录/文件 |
| --- | --- | --- |
| 入口装配层 | 负责启动、初始化顺序、任务创建、对象装配 | `main.c` |
| 应用编排层 | 负责运行时协调、命令分发、跨模块业务流程 | `App/Inc`、`App/Src` |
| 领域功能层 | 负责项目专属业务能力 | `Video`、`Diagnostics`、`Rom` |
| 可复用基础设施层 | 负责可跨项目复用的基础能力 | `Audio`、`Vdma`、`Storage` |
| 硬件访问与平台适配层 | 负责项目专属寄存器访问和 BSP 交互 | `Gba`、平台/BSP |

### 5.3 当前依赖关系

推荐理解为：

`main.c -> App -> { Video, Diagnostics, Rom, Audio, Vdma, Gba, Storage, Common }`

`Rom -> Storage`

`Video -> { Vdma, Gba, Common }`

`Diagnostics -> { Video, Gba, Audio, Common }`

`Audio / Vdma / Storage -> 平台/BSP`

### 5.4 明确禁止的依赖

以下依赖一律禁止：

- `Storage -> Rom`
- `Audio -> App`
- `Vdma -> Video`
- `Gba -> App`
- `Diagnostics -> App`
- 任意模块反向依赖 `main.c`
- 任意功能模块直接依赖完整 `PsAppContext`
- 任意两个同层领域模块形成环依赖

## 6. 目录结构规范

### 6.1 目录总览

```text
src/
├─ main.c
├─ ARCHITECTURE.md
├─ App/
│  ├─ Inc/
│  └─ Src/
├─ Audio/
│  ├─ Inc/
│  └─ Src/
├─ Common/
│  ├─ Inc/
│  └─ Src/
├─ Diagnostics/
│  ├─ Inc/
│  └─ Src/
├─ Gba/
│  ├─ Inc/
│  └─ Src/
├─ Rom/
│  ├─ Inc/
│  └─ Src/
├─ Storage/
│  ├─ Inc/
│  └─ Src/
├─ Vdma/
│  ├─ Inc/
│  └─ Src/
└─ Video/
   ├─ Inc/
   └─ Src/
```

### 6.2 `Inc/Src` 规则

每个模块目录原则上都应拆分为：

- `Inc`：对外公开的稳定接口、必要类型、公开常量
- `Src`：实现文件、静态函数、内部辅助逻辑

约束如下：

1. `Inc` 中不得暴露不必要的内部实现细节。
2. `Inc` 中优先暴露抽象后的最小上下文，而不是完整应用对象。
3. `Src` 中允许存在模块内部 `static` 辅助函数。
4. 一个 `.c` 文件的职责应尽量单一，不要同时承担初始化、控制台、业务、诊断四种角色。
5. `main.c` 是根入口，允许放在 `src` 根目录，不强制进入 `App/Src`。

### 6.3 模块归类规则

新增代码时，必须先判断其归属：

| 类型 | 应放目录 | 判断标准 |
| --- | --- | --- |
| 公共状态、组合根、工程级常量 | `Common` | 被多个上层模块共享，但不属于某个领域 |
| 运行时协调、命令分发 | `App` | 负责“调谁、何时调、按什么顺序调” |
| 项目专属显示链路、帧逻辑 | `Video` | 与 GBA/本项目视频链路强相关 |
| 审计、追踪、诊断 | `Diagnostics` | 只观察与输出，不主导业务 |
| 项目专属寄存器访问 | `Gba` | 与本项目寄存器定义强绑定 |
| 通用文件系统读写 | `Storage` | 可被 ROM、配置、资源等复用 |
| 领域装载逻辑 | `Rom` | 基于 `Storage` 实现 ROM 业务 |
| 通用音频驱动 | `Audio` | 不依赖 GBA 业务语义 |
| 通用 VDMA 包装 | `Vdma` | 不依赖项目视频业务语义 |

## 7. 模块职责定义

### 7.1 `Common`

职责：

- 存放工程级共享状态定义
- 存放组合根对象
- 负责完整对象与窄上下文之间的装配

当前关键文件：

- `Common/Inc/ps_app_state.h`
- `Common/Inc/ps_app_context.h`
- `Common/Src/ps_app_context.c`

约束：

- `ps_app_state.h` 只放纯状态定义，不放业务逻辑
- `ps_app_context.h` 只用于组合根，不作为普通功能模块依赖入口

### 7.2 `App`

职责：

- 承担应用级编排
- 处理初始化顺序
- 处理命令行交互
- 协调 Video、Diagnostics、Rom、Audio 等模块

不负责：

- 不直接实现底层驱动细节
- 不直接实现视频缩放算法
- 不直接实现文件系统读写细节

### 7.3 `Video`

职责：

- 处理采样帧到 HDMI 帧的呈现链路
- 管理显示帧切换
- 管理视频相关的中断回调和恢复逻辑

依赖：

- `Vdma`
- `Gba`
- `Common`

不应依赖：

- `Diagnostics`
- `App`
- `UART`
- `Audio`

### 7.4 `Diagnostics`

职责：

- 观察系统状态
- 输出诊断日志
- 进行链路探针、追踪、审计和异常转储

依赖特点：

- 允许观察多个模块
- 允许读取 Video/Gba/Audio/Common 信息
- 不负责业务主流程，不得反向掌控 App

### 7.5 `Gba`

职责：

- 封装本项目专属 GBA 寄存器访问
- 统一寄存器读写和控制行为

约束：

- 业务代码不得绕过 `Gba` 模块直接拼寄存器地址
- 若新增寄存器行为，应优先在 `Gba` 层补充 API，而不是在上层直接写寄存器

### 7.6 `Storage`

职责：

- 统一文件系统访问
- 隔离 FatFs 细节

约束：

- 上层业务模块不应直接包含 FatFs 细节头文件
- `Storage` 只提供“读取/装载/枚举”等通用能力，不承载 ROM 业务语义

### 7.7 `Rom`

职责：

- 负责 ROM 领域规则
- 把 ROM 从外部存储装入目标区域
- 维护 ROM 状态及装载结果

依赖：

- `Storage`
- `Common`

不应依赖：

- `FatFs` 直接细节
- `Console`
- `Diagnostics`

### 7.8 `Audio`

职责：

- 管理音频编解码器初始化与参数设置

属性：

- 基础可复用模块
- 不应携带项目业务状态

### 7.9 `Vdma`

职责：

- 对 AXI VDMA 提供统一初始化、停车、填充等能力封装

属性：

- 基础可复用模块
- 不应了解 GBA 帧捕获语义

## 8. 上下文模型规范

### 8.1 当前上下文拆分

当前已形成以下对象模型：

| 类型 | 作用 |
| --- | --- |
| `PsAppContext` | 完整应用对象，仅组合根使用 |
| `PsAppRuntimeContext` | 运行时编排视图 |
| `PsAppConsoleContext` | 控制台编排视图 |
| `PsAppVideoContext` | 视频模块最小依赖视图 |
| `PsAppDiagContext` | 诊断模块观察视图 |
| `PsAppShadowConfig` 等 | 纯状态载体 |

### 8.2 上下文使用原则

1. 完整 `PsAppContext` 只能在组合根和装配逻辑中出现。
2. 业务模块对外只暴露“自己需要的最小视图”。
3. 纯状态与驱动句柄分离，避免某一状态变更导致所有模块头文件联动。
4. 上层编排通过窄上下文组合底层模块，而不是传递整棵对象树。

### 8.3 头文件暴露原则

以下规则必须遵守：

1. 模块公共头文件不应包含完整 `ps_app_context.h`。
2. 模块若只需要状态定义，应包含 `ps_app_state.h`。
3. 模块若只需要某个窄视图，应包含该模块对应的 `*_context.h`。
4. 若可以使用前向声明，则优先前向声明，减少头文件级联依赖。

### 8.4 组合根说明

组合根负责以下工作：

- 创建完整应用对象
- 清零或初始化对象
- 绑定各子上下文中的指针关系
- 调用初始化流程
- 创建 FreeRTOS 任务

组合根之外，其他模块只应消费已装配好的窄视图，不应再次重组依赖关系。

## 9. 编译期耦合控制规则

### 9.1 必须遵守

1. 新增公共头文件时，先判断是否真的需要暴露驱动类型。
2. 若一个字段只在实现文件中使用，不应把它放进公共头文件。
3. 若一个模块只需要只读状态，优先使用 `const` 指针视图。
4. 若一个模块只需要两个对象，不得为了省事传入“总上下文”。

### 9.2 明确禁止

以下做法禁止：

- 在 `Video/Inc` 中引入 `App` 头文件
- 在 `Diagnostics/Inc` 中暴露控制台命令逻辑
- 在 `Storage` 中掺入 ROM 装载业务
- 在 `Audio`、`Vdma` 里加入项目业务字段
- 在任意模块公共头文件里塞入不必要的大量平台头文件

### 9.3 评审检查项

代码评审时，必须检查：

- 新增 `#include` 是否扩大了模块可见面
- 公共头文件是否引入了不必要的依赖
- 是否把本应属于 `Storage` 的逻辑写进了 `Rom`
- 是否把本应属于 `Gba` 的寄存器行为写进了上层
- 是否出现“为了方便”重新把完整上下文传来传去

## 10. 文件命名与组织规范

### 10.1 命名规则

推荐命名方式：

- `ps_<模块名>_<职责>.h/.c`

例如：

- `ps_app_runtime_boot.c`
- `ps_app_runtime_rom.c`
- `ps_app_runtime_service.c`
- `ps_app_console.c`
- `ps_app_console_diag.c`
- `ps_app_console_runtime.c`
- `ps_app_console_media.c`
- `ps_app_video.c`
- `ps_app_diag.c`
- `ps_fatfs_storage.c`

### 10.2 文件粒度规则

一个文件应围绕一个稳定职责组织：

- 运行时初始化放在 `runtime_boot`
- ROM/BIOS 装载与识别放在 `runtime_rom`
- 运行时服务循环与任务入口放在 `runtime_service`
- 控制台分发放在 `console`，命令域实现拆分到 `console_diag` / `console_runtime` / `console_media`
- 视频呈现放在 `video`
- 诊断输出放在 `diag`

USB Host 的实现层进一步按职责分层：

- `ps_app_usbhost_ulpi.c`：ULPI/PHY 与寄存器控制
- `ps_app_usbhost_enum_recovery.c`：枚举恢复与低层回调
- `ps_app_usbhost_report_channel.c`：中断报告通道与 sideband
- `ps_app_usbhost_impl_internal.h`：内部上下文与模块协作契约

若某文件超过合理规模，优先继续按职责拆分，而不是继续向单文件堆逻辑。

### 10.3 静态辅助函数

仅供单文件内部使用的函数必须声明为 `static`，避免污染模块导出面。

## 11. 典型运行流程

### 11.1 启动流程

推荐顺序如下：

1. 使能 Cache
2. 初始化完整应用对象
3. 初始化 UART
4. 初始化寄存器访问层
5. 初始化 VDMA
6. 初始化 Video 中断
7. 初始化 Audio
8. 准备初始显示帧
9. 自动装载 ROM
10. 输出启动审计
11. 创建监控任务与控制台任务
12. 启动调度器

### 11.2 运行时服务流程

运行时循环主要职责：

- 读取状态寄存器
- 检查 IRQ
- 触发视频帧呈现
- 执行 VDMA 恢复
- 进行异常审计
- 进行延迟诊断和帧扫描

### 11.3 ROM 装载流程

ROM 装载推荐责任划分如下：

1. `App` 决定何时触发装载
2. `Rom` 负责装载领域规则
3. `Storage` 负责从文件系统读取内容
4. `Gba` 负责寄存器控制和状态提交
5. `Video` 负责装载后显示链路同步
6. `Diagnostics` 负责装载前后审计输出

## 12. 新增功能时的落位规则

### 12.1 新增可复用基础模块

若新增模块满足以下条件，应优先放入独立基础模块：

- 不依赖 GBA 项目语义
- 在其他 FPGA/嵌入式项目中也可复用
- 本质上是驱动、适配或通用能力封装

示例：

- 新增 `SpiFlash`
- 新增 `I2cEeprom`
- 新增 `FrameBufferUtils`

### 12.2 新增项目专属模块

若新增模块满足以下条件，应归入项目专属层：

- 强依赖本项目寄存器、地址空间、链路时序
- 业务语义只对当前项目成立
- 与 GBA 数据格式或本项目调试链路绑定

示例：

- 新增 `SaveState`
- 新增 `JoypadMapper`
- 新增 `BootAudit`

### 12.3 新增字段时的放置规则

新增字段前，必须先判断其性质：

| 字段性质 | 放置位置 |
| --- | --- |
| 工程共享纯状态 | `ps_app_state.h` |
| 组合根装配关系 | `ps_app_context.h/.c` |
| 模块内部私有缓存 | 对应模块 `Src` 的内部静态或私有结构 |
| 通用驱动状态 | 对应基础模块内部结构 |

## 13. 扩展与重构约束

### 13.1 优先使用“补充窄视图”而不是“回退到总对象”

当某模块需要新增依赖时，应优先：

1. 评估该依赖是否合理
2. 若合理，则在该模块上下文中增加最小必要字段
3. 在组合根中完成装配

禁止直接把完整 `PsAppContext` 重新传回模块。

### 13.2 优先补低层 API，不直接穿透低层实现

例如新增寄存器行为时：

1. 优先在 `Gba` 模块新增 `PsGbaRegs_*` API
2. 上层调用该 API
3. 禁止在上层直接拼地址和位域

### 13.3 诊断代码不得反客为主

诊断代码可以观察、打印、审计，但不得逐步演变为新的业务编排中心。
若某段诊断逻辑开始决定系统业务流程，应重新评估是否应迁回 `App`。

## 14. 反模式清单

以下是必须持续避免的反模式：

### 14.1 上帝对象

表现：

- 一个上下文包含所有句柄、所有状态、所有行为入口
- 任何模块都接收同一个总对象

处理原则：

- 拆成纯状态、驱动句柄、窄服务视图

### 14.2 横向穿透调用

表现：

- 业务模块跳过正式边界，直接操作底层寄存器或文件系统

处理原则：

- 回收至 `Gba`、`Storage` 等边界模块

### 14.3 工具模块业务化

表现：

- `Audio`、`Vdma`、`Storage` 等基础模块开始携带项目业务状态

处理原则：

- 业务状态回收到 `App` 或领域模块

### 14.4 诊断模块控制业务

表现：

- `Diagnostics` 中开始出现业务流程分支和状态推进

处理原则：

- 诊断只观察，不主导

## 15. 代码评审标准

每次涉及 PS 端软件结构调整时，至少检查以下问题：

1. 该代码是否放在了正确目录？
2. 该模块是否只承担单一职责？
3. 该头文件是否暴露了不该暴露的依赖？
4. 该修改是否引入了反向依赖或环依赖？
5. 该功能是否应该抽成可复用模块？
6. 该模块是否错误依赖了完整 `PsAppContext`？
7. 该状态是否应该放在 `ps_app_state.h` 而不是某个业务头文件中？

## 16. 后续演进建议

在当前第三轮解耦基础上，下一阶段建议继续推进：

1. 将 `App/Src/ps_app_console.c` 按命令域继续拆分，例如 `audio_cmd`、`rom_cmd`、`diag_cmd`、`video_cmd`。
2. 将 `Diagnostics` 中体量较大的输出能力继续拆为 `trace`、`audit`、`probe`、`fbscan` 子文件。
3. 逐步收紧公共头文件的包含范围，更多使用前向声明。
4. 若后续出现保存状态、配置管理、输入映射等能力，应优先新增独立领域模块，而不是堆回 `App`。

## 17. 架构结论

本工程 PS 端软件的核心原则可以概括为：

- 入口唯一装配
- 编排与业务分离
- 业务与驱动分离
- 项目专属与可复用分离
- 总上下文仅用于组合根
- 业务模块只依赖窄上下文
- 公共状态独立定义
- 依赖方向严格单向

后续所有 PS 端代码调整，均应以本文档为准绳执行。若实现与文档冲突，应优先修正实现；若确需突破文档，应先更新本文档并说明原因，再落代码。
